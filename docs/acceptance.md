# 实现验收

## 自动化检查

2026-10-06，在 Windows 本地通过 25 项离线测试（7 项单元测试、18 项集成测试）。覆盖认证加密篡改/上下文校验、主密钥重新解锁、数据库及 WAL 明文检测、并发队列容量、重复 Bot 更新、逐页提交与稳定序号、恢复与不确定发送核对、相册任务持久化、UTF-16 深链解析、会话加密持久化、Web 登录/CSRF/注销、配置上限、双执行通道隔离、媒体消息定位持久化、原 Python HV1 加密样本兼容与重复导入。消息读取回归覆盖处理中占位提示不触发重发、空结果明确结束、更新流遗漏后的历史回读及原消息编辑、取消与写回竞争、取消后重启不重新排队，以及手动重试重置尝试次数。搜索翻页新增末页只移除按钮、独立结束提示、相同正文的新消息及无响应不误报完成四项回归。

翻页点击返回的结束提示会终止搜索；`BOT_RESPONSE_TIMEOUT` 只表示按钮没有被确认，仍回读消息判断是否已更新。已保存页之后的等待超时显示 `search_partial_timeout` 和保存页数，可用 `/search 关键词 continue` 续搜。不会仅凭声明总页数或无响应认定搜索完成。

本机服务使用隔离配置和合成数据，已验证 CLI 状态查询、Web 登录与任务提交、在线 SQLite 备份、静态页面 HTTP 200，以及注销后的 HTTP 401。未填写 Telegram 凭据，合成搜索任务按预期以 `missing_api_credentials` 结束。此结果不代表真实 Telegram 传输已验收。

`cargo fmt --all -- --check`、严格 Clippy 和 Windows Release 构建通过。Release 服务另通过重启后任务读取、负数聊天 ID 设置、Web 登录和在线备份检查。首次公开仓库 CI 已在 Linux 通过完整检查、测试和发布构建；后续修复的 CI 状态以对应提交的 GitHub Actions 为准。仍未进行真实 VPS 传输和资源压测。

## 真实链路验收

当前开发环境为 Windows。以下必须使用测试账号/目标在 Linux VPS 实测，自动化离线测试不能证明已通过：

1. 主账号/上传账号、二步验证、SOCKS5、重连和 DC 迁移。
2. 搜索占位消息编辑、排序、原消息续搜、重新定位、限流。
3. 分批领取的最后一组、按钮原地编辑、“全部获取”、未知文件数量。
4. 单账号和双账号引用复制、相册和文件引用过期。
5. 图片、视频、音频、语音、大文件下载上传及停止。
6. 转发媒体的 copy 和 deep 回读、标签编辑权限。
7. 网络断开、磁盘不足、任务中 kill、发送成功但本地未落账。
8. 0.5 CPU/1GB cgroup 下 72 小时稳定性、RSS/cgroup 内存和传输速度。

## 当前边界

- MTProto 原生代理仅支持 SOCKS5，旧版 SOCKS4/HTTP 代理需要换 SOCKS5 入口。
- 账号登录通过 CLI；Web 负责日常管理。
- deep 转存逐文件发送，相册外观可能拆开；Bot API copy 聚合相册。
- 重传保留说明、文件名及音视频主要属性；缩略图和全部特殊属性需进一步真机验证。
- 取消仅保证停止本地继续调度；已经发出的远端请求可能仍完成。发送意图未核对时进入 review。
- 没有单文件字节级续传、密码更换及旧转存记录手动映射命令。
- `/log` 与 Web 运行记录显示任务事件摘要；完整结构化诊断日志在 journald/标准输出。
