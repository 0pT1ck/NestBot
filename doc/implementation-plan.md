# Rust Telegram 实时关注提醒计划

项目文件位置、目录归类、Git 开发流程及作者署名以根目录 `CLAUDE.md` 为准。本计划保存在 `doc/implementation-plan.md`；后续项目文档统一归入 `doc/`。

> 实施状态（2026-10-20）：已获用户授权开始编码，现已建立首版工程。本文保留目标设计，不代表所有目标均已达成。实际支持范围见 README.md、doc/deployment.md 和 doc/telegram-library-audit.md。真实账号双次转发、Linux 安装及内存测试未验收；依赖存在无法可靠识别全部隐式重连的已知限制。自动升级、备份及回滚未实现，安装器明确拒绝不同版本覆盖；不将首版称为生产就绪。

## Context
用户需要一个低内存 Rust 服务：用已入群的个人账号读取指定群的新消息，命中自己标记的发言人后，将原消息原生转发给自己，并提供回到原群原消息的入口。已确认：Bot 无法加入源群；通过私聊 Bot 管理关注名单；部署 Linux 小内存 VPS；仅实时提醒，不主动补发停机历史。初次调研时工作区仅有 .git，原项目文件全部处于未提交删除状态，没有现存源码可复用；当前已新增根目录 CLAUDE.md 和本计划，尚无新 Cargo 工程。不恢复旧文件、不处理原有删除、不提交 Git；当前阶段只维护计划和约束。新增部署硬性要求：用户指定一个目录即可一键部署，程序及全部应用本地数据在该目录内归类存放，不拆分安装。

## 推荐方案
单个 Rust 二进制、单进程：

个人账号 MTProto 新消息 → 按 (源群 ID, 发言用户 ID) 过滤 → 个人账号原生转发到私有中转超群 → Bot API 从中转群原生转发到自己的私聊 → 发送附“查看原消息”按钮的提醒。

- 中转超群只包含自己与 Bot，不邀请第三人；仅作为转发暂存，不监听它触发业务。
- 个人账号拿到转发结果中的中转消息 ID 后，直接交给进程内通知模块；不依赖 Bot 再收到中转群 update，也不靠转发署名反推来源。
- Bot 只使用 HTTP Bot API；不建立第二个 MTProto 客户端、不用 TDLib、不启 Web 服务。
- 中转方案是待批准的设计要求：需要用户创建中转超群、加入 Bot，并先私聊 Bot /start。先用真实测试消息验证双次转发的客户端表现，再实现完整功能。
- 两段原生转发均请求静音，中转群也在客户端设为静音；最终另发一条非静音提醒，避免双重响铃。验证 MTProto 高层接口是否支持 silent，必要时使用少量底层请求。是否真正弹窗/响铃仍由 Telegram 客户端及用户通知设置决定。
- 中转涉及 Telegram 云端暂存，需随方案一起获得用户批准；成功后清理只能减少留存，不能保证失败或崩溃时即时删除。

## 功能与权限边界
- 第一版监听范围为超级群中具有可识别个人 user_id 的新增普通消息；文本、图片、视频、文件通过 Telegram 服务端转发，不下载附件。广播频道帖子、匿名管理员及以频道身份发出的消息不属于首版按个人关注的支持范围；不能将频道 ID 当作用户 ID，也不能根据作者签名推导个人身份。/groups 明确标注可监听对象，/watch 对不支持的源聊天或发言主体明确拒绝，而不是接受永远无法命中的规则。
- 对普通群成员消息，点击转发者署名不一定回到原消息。始终依据监听时保存的源 chat/message ID 生成独立原文链接；频道转发自带的来源跳转作为附加能力。
- 公有超级群/频道使用 https://t.me/<username>/<message_id>，私有超级群/频道使用 https://t.me/c/<裸 channel ID>/<message_id>。封装 ID 类型转换，不能把 Bot API 的 -100 前缀拼进去；论坛主题单独测试。点击者仍须具备源群访问权限。
- 基础群可能没有可用消息链接：添加时明确报告限制；要求升级超级群才能满足“原文跳转”验收，不伪造链接。
- 禁止转发的内容不复制、不下载来绕过；只发不包含受保护正文的失败提示及可用链接。删除消息、服务消息及权限不足均明确处理。
- 匿名管理员、以频道身份发言、隐藏身份转发无法推导背后的个人 ID，不冒充普通用户匹配。以实际发言者身份为准，而不是消息的原始转发作者。
- 不回填历史、不处理编辑/删除同步，不批量扫描成员，不做多用户 SaaS、Web 面板或搜索索引。相册首版按单条消息转发，暂不保证相册组合与提醒合并。

## 管理与持久化
- 所有命令同时检查 private chat、owner user ID 和目标 chat ID；默认拒绝其他用户及群内管理命令。
- 建议命令：/groups（分页选择账号可见会话）、/watch <群ID> <用户ID或@用户名>、/unwatch <群ID> <用户ID>、/list、/status、/help。
- 用户名仅在添加时解析，持久化稳定的数值 ID，避免改名或名称重新注册造成误匹配；无用户名的成员支持直接填写用户 ID，不承诺 Bot 能从任意转发消息中识别隐藏用户。
- 静态设置用 config/config.toml，关注规则用小型 data/watches.toml 原子替换保存；写成功才确认命令成功。读入内存形成按群分层的 HashSet，限制规则数量，写入串行化。错误配置不静默清空。
- MTProto 授权及必要 peer 状态使用选定库支持的持久 session 存储；与规则文件分开。若其实现使用 SQLite，则复用现有存储，不为业务额外引入数据库服务。
- 独立 login 子命令首次交互获取验证码/2FA并保存 session；后台 run 不等待验证码、不循环重新登录。
- Bot token、api_hash 及 session 不入 Git/日志；Linux 敏感文件/目录权限分别为 0600/0700，以拥有部署目录的非 root 用户运行，不要求安装时新增系统用户。session 等同账号凭据，需重点保护。

## 低内存与实时语义
- 首选评估 grammers-client 0.11.x；锁定通过验证的依赖版本，不直接套用旧版 grammers 配置。HTTP 使用最小功能 reqwest + rustls，序列化 serde/toml，日志 tracing，关闭无关默认 features；优先评估 Tokio current_thread。
- 内存只持有有界关注规则、短任务队列、少量去重键和必要 session/peer 信息。匹配前不克隆完整消息；任务只保存 ID、状态、有限长度群名/标签与源链接信息。
- 初始建议应用任务容量 128、Bot getUpdates limit 20、转发工作者 1、去重缓存最多 2048 条且 TTL 10 分钟。所有数字可配置并设合法上限。
- 不缓存正文、不下载媒体、不维护全群成员或历史集合、不每条消息 resolve 用户名、不为每条消息无界 tokio::spawn。
- 必须审查库底层 update 接收队列、session peer 缓存、HTTP/TLS 缓冲和 runtime 线程数；应用层有界队列不代表进程内存有界。grammers 0.11 的 UpdatesConfiguration 已验证只有 catch_up，默认 false；不能虚构 update_queue_limit。若底层无界，先验证可控实现，再决定最小适配，不在验证前承诺内存上限。
- 实时策略：catch_up=false；启动时丢弃 Bot 旧命令并建立新消息时间边界；重连建立新边界并丢弃积压旧消息，不主动查询历史。底层协议状态同步与业务历史补发分开；验证库重连行为。若无法可靠观察重连边界，不能用 60 秒 TTL 冒充严格“不补断线消息”，应作为先行验证的阻塞项；同时要求系统时钟同步。
- 队列满时不无限阻塞源 update 消费，不让库内部积压替代应用队列；按明确策略丢弃新任务并累计丢弃计数，恢复后合并告警。第一版接受故障/过载期间漏提醒，不声称不丢消息。
- MTProto FloodWait 按服务端等待时间暂停相关 MTProto 请求，接收过滤继续运行；非阻塞计时。所有 Bot 出站发送（转发、提醒、命令回复、失败提示和恢复告警）统一经过一个有界发送调度器，共享同一 Bot 的冷却截止时间；收到 429 时遵守 retry_after，首版保守暂停该 Bot 的全部出站发送，其他路径不得绕过。Bot API 长轮询保留独立接收路径并处理自身的错误退避；告警合并且受同一限流控制。所有出站队列计入总容量预算，不为控制消息新增无界队列；命令回复预留有限容量，关注规则保存成功后才能安排成功回复。重试限制次数及任务年龄（消息转发任务建议 60 秒），过期丢弃并计数；绝不忙重试。
- 分阶段记录中转/私聊转发/提醒状态，已成功步骤不重复执行。有限去重只覆盖本进程运行期；发送超时可能结果不确定，Bot API 无幂等键，不能保证 exactly-once。未知结果不盲重试，记录并提示可能漏发或重复。
- 中转内容在成功通知后尝试删除，失败仅有限重试；建议开启中转超群自动删除作为清理兜底。此行为在实施前明确验证原生来源和原文链接不会受影响。
- 内存验收以 Linux release RSS/PSS 实测为准：暂定空闲 RSS ≤64 MiB 的优化目标而非保证。记录平台、依赖、规则/会话数和负载；稳定负载持续运行无无界增长优先于未经测量的数字。

## 单目录部署设计（硬性要求，待实现）

### 发布布局

所有应用本地文件集中在用户指定的一个根目录，例如 `/home/bot/nestbot/`；允许内部分类，不允许拆到系统目录。预编译发布包按支持的 Linux 架构提供，在实际目标环境验证运行库需求，不承诺未经测试的平台都能运行；目标 VPS 不需要 Rust 工具链或外部数据库服务。

```text
<root>/
  bin/nestbot            # 程序
  config/              # config.toml、受限权限的凭据文件
  data/                # watches.toml、session、SQLite 及 WAL/SHM
  logs/                # 有容量上限的应用日志
  tmp/                 # 临时文件、独立下载目录、升级暂存
  run/                 # 单实例锁及运行控制状态
  backups/             # 停机一致性备份、有限保留的旧版本
  scripts/             # install.sh、start.sh、stop.sh、status.sh
  doc/                 # 部署、运行及故障处理说明
```

- 开发源码的部署脚本位于 `deploy/`，打包时进入发布包 `scripts/`。发布构建和打包产物在仓库 `target/` 内，不写外部临时目录。
- 发布包解压至目标目录后，一条 `sh <root>/scripts/install.sh --root <root>` 完成本地安装检查与初始化；这是计划中的接口，不是当前可用命令。默认不使用 curl 管道执行脚本、不安装全局依赖、不需 sudo、不注册系统服务。
- 安装器检查目标目录所有权、权限及已有内容；允许经发布清单校验的刚解压目录初始化，已有实例先识别，未知非空目录拒绝盲目覆盖。安装可重跑，只修改自身管理的文件，不递归清空目录，不覆盖已有凭据、session 和关注规则。重装/升级不能先把整个发布包覆盖解压到活动目录，应先解压到根内独立 tmp/ 子目录再由安装器执行受控替换。
- 首次凭据与 Telegram 验证码/2FA 必须由用户完成。无人值守调用发现未配置或未登录时明确退出并给出下一步，不无限等待，也不假装部署已可用。用户还需先准备 Bot 与中转群。

### 路径与进程管理

- 统一根目录解析器：显式 `--root` 优先，否则从真实可执行文件 `<root>/bin/nestbot` 推导。开发二进制位于 `target/` 时必须显式传入仓库根；不得把 `target/debug` 意外当作数据目录。
- 启动脚本根据脚本实际位置确定根并显式传给程序；从其他工作目录启动、带空格路径启动和目录整体迁移都使用同一逻辑。登录与运行必须访问同一 session。
- 所有写路径限定在根内，拒绝目录穿越、根外绝对路径及符号链接逃逸；检查已有父目录及新建路径。目录不与不可信用户共享写权限。原子替换文件与目标同目录，临时目录和数据库侧文件显式定位，禁止静默回退到系统临时目录。
- 默认目录内脚本负责启动/状态/停止：标准输出与错误重定向到根内的有界日志，应用持有单实例锁，停止时验证实例身份，不根据 PID 文件盲目 kill；优雅退出并关闭数据库后才宣告停止成功。
- 默认不部署 systemd 单元、全局启动链接、外部 PID 文件或外部日志。这样不自动获得开机自启/系统级故障拉起；若用户以后需要，另行批准系统注册文件例外，不能一边写入 `/etc/systemd` 一边声称所有文件都在根内。
- Telegram 云端消息仍在 Telegram；单目录要求指应用本地文件，不新增消息归档或媒体下载功能，也不承诺控制操作系统自身审计记录。

### 升级、备份和迁移

- 校验平台、发布版本及通过可信渠道取得的校验值；下载/解压仅在根内独立 `tmp/` 子目录，拒绝归档绝对路径、`..` 和逃逸链接。
- 升级先停止原实例并核实退出，在根内备份受影响的状态和旧程序，再替换受管理的程序/脚本；保持现有配置和授权。失败保留可恢复的旧版本；有状态迁移时按兼容性回滚程序和状态，不能仅换回二进制。
- 备份在应用停止、数据库关闭后完成，不能把运行中 SQLite 的单个主文件复制当作有效备份。备份按清单仅包含程序版本、配置与状态，排除 backups/、tmp/、run/ 和旧日志，避免在根内备份时递归打包自身。备份和升级暂存设保留上限；默认不压缩媒体或群历史，因为不保存这些内容。
- 迁移流程为“停止 → 整目录复制并保留权限 → 新位置启动 → 验证 session 和规则”，旧实例不得同时运行。不保留硬编码旧绝对路径。

## 分阶段实施及关键文件（批准后新建）
1. **安全准备与可行性验证**：在首次构建、写凭据或登录前先创建 .gitignore，覆盖实际凭据、data/、logs/、tmp/、run/、backups/、target/ 等本地路径，配置样例仍可跟踪；建立根内路径与敏感目录权限后再试验。只在用户自有测试群验证个人账号登录、新消息接收、个人账号→中转超群→Bot 私聊的双次原生转发、原文跳转、媒体零下载、session 复用和底层队列/缓存。若关键能力失败先修订方案，不继续扩展。
2. **最小骨架和监听匹配**：Cargo.toml、src/main.rs、src/config.rs、src/telegram.rs、src/filter.rs；login/run 两种运行模式、严格源群/用户过滤、实时边界和有界任务调度。
3. **转发通知与管理**：src/relay.rs、src/bot.rs、src/rules.rs；中转关联、链接生成、Bot API 长轮询、owner-only 命令、规则原子持久化及失败处理。
4. **低内存和单目录部署**：配置样例、deploy/install.sh、deploy/start.sh、deploy/stop.sh、deploy/status.sh、doc/deployment.md、README.md；实现统一根目录解析（src/paths.rs）、单实例管理、目录内日志/暂存/备份和可重跑安装。默认不创建或注册 systemd 单元；凭据安全、有限日志、重试/去重/限流、Linux 内存分析一并验收。内存剖析后才考虑 allocator 或进一步依赖裁剪，不预先增加复杂度。
5. **测试**：tests/ 下增加规则匹配、命令权限、链接转换、队列边界与转发状态测试；脚本只在有明确需要时添加。

## 验证与验收
- cargo fmt --check、cargo clippy --all-targets -- -D warnings、cargo test；cargo tree -e features 检查功能依赖。
- 单元测试：群/用户交叉匹配、改名不影响 ID、匿名身份不误匹配、owner-only、损坏规则文件、原子写失败、公开/私有/论坛链接、时间边界、队列饱和、缓存过期和步骤级重试。
- Mock Bot API/MTProto 适配：FloodWait、429、权限不足、受保护内容、删除、部分步骤失败和网络超时；验证不会忙循环、重复成功步骤或无界增长。额外验证通知触发 429 后命令回复/失败提示/告警均遵守共享冷却，所有出站路径合计容量有界；添加广播频道或频道身份规则被明确拒绝，不能形成静默不命中的关注规则。
- 真机端到端：自有源超级群中目标用户发文本/图片/视频/文件，个人账号已入群、Bot 不在源群；私聊收到原生转发及带原文按钮提醒，按钮回到正确消息；非目标用户/其他群不触发；禁止转发不绕过。
- 确认客户端是否保留两次转发的源信息、转发静音+提醒非静音表现，中转清理后最终转发仍可读且原文按钮可用。
- 重启保留关注规则和 session，无需重新登录；断网重连不主动补旧消息；Bot 旧命令不在启动后重放；session 失效给出明确诊断。
- 模拟输入做过载与长时测试，不向 Telegram 压测；持续 24 小时记录空闲/正常/突发负载的 RSS/PSS、峰值、队列长度和丢弃计数，验证容量上限与资源稳定性。
- 单目录验收：普通非 root 用户在没有 Rust 工具链的目标 Linux 上，以一条安装命令完成初始化；首次登录后可启动。测试空目录、重复安装、未知非空目录、带空格路径及从任意工作目录运行。
